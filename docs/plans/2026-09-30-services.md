# Services — the layer between commands and the messenger and store

Status: **approved 2026-09-30** (NEED-413 A: keep save-on-read as the `stored` decorator). Step 2 of the layer design the owner approved on
2026-09-30 (max-cli's private `docs_ai/plans/2026-09-30-layers.md`; NEED-406 B, NEED-407 A,
NEED-408 A). This plan covers cli-messaging only. max-cli moves onto the services later (steps 5–6
there).

## Goal

Every use case lives **once**, in a service, and commands and MCP tools only call it and render the
answer. A CLI replaces one service method, and can call the shared one inside its replacement. No
behaviour change: every existing test passes unchanged, and tg-cli works without edits.

## Where we are

- Commands choose the source themselves: `messages list` runs
  `offline ? withStore(store.messages) : withMessenger(connection.history)`
  (`src/cli/messenger/messages-command.ts:47-60`); `readWindow` does the same for `context` and
  `show` (:91-111); `search` goes to the store (:125-132).
- MCP tools repeat that logic: `messages_list` calls `history`/`historyAfter` itself
  (`src/mcp/tools/messages.ts:31-55`).
- Some use cases are already shared functions: `guardedSend` (`messages-command.ts:272`), the
  `guarded*` helpers, `unreadIn`/`newIn` (`inbox.ts:46,73`), `reviewIn` (`review.ts`),
  `storedChatId` (:380).
- Save-on-read is the `stored` decorator on the adapter (`stored.ts:22`); run events are `observed`
  (`observed.ts:11`); both stacked by `connected()` (`context.ts:68-96`).
- A connection is opened per command by `withMessenger` and closed after (`context.ts:109-129`); the
  store by `withStore` (:130-147). The MCP session holds one connection for minutes (`mcp/session.ts`).
- A CLI overrides only by replacing a whole command factory (`cli/program.ts:17-23`).

## Decisions

**S1 · A service is a plain object made by a factory, over lazy dependencies.**

```ts
// src/services/deps.ts
export interface ServiceDeps {
  messenger: Messenger                              // the CLI's description: provider, savedChatId, …
  offline: boolean
  account: () => Promise<AccountKey>                // recalled for --offline, from `me` online
  connection: () => Promise<MessengerAdapter>       // opened on first use, already `stored` + `observed`
  store: () => Promise<MessageStore>                // opened on first use
  guard: SendGuard
}
```

A command that reads only the store never connects; one that never touches the store never opens
it — as today. Who opened them closes them (S3).

**S2 · The services, and what moves into each.**

```ts
// src/services/messages.ts
export interface MessagesService {
  list(chat: string, window: { limit: number; before?: Id; after?: After }): Promise<Page<Message>>
  around(chat: string, message: Id, window: Window): Promise<WindowedMessage[]>
  show(target: Target): Promise<Message>
  search(query: { text?: string; pattern?: RegExp; chat?: string; limit: number }): Promise<Page<StoredHit>>
  send(chat: string, text: string, options: SendRequest): Promise<Sent>        // through the guard
  edit(target: Target, text: string): Promise<Message>
  delete(target: Target, options: { forEveryone: boolean }): Promise<Deleted>
  forward(target: Target, to: string): Promise<Sent>
  pin(target: Target, options: PinOptions): Promise<void>
  unpin(chat: string): Promise<void>
  react(target: Target, reaction: string | null): Promise<Reactions>
}
export const messagesService = (deps: ServiceDeps): MessagesService => …
```

| Service | Takes over |
|---|---|
| `messages` | the list/context/show/search branches; `guardedSend`, `guardedEdit`, `…Forward`, `…Pin`, `…Delete`, `…Reaction` |
| `chats` | `chats list/show/members/events/read`; `guardedMarkRead` |
| `people` | `contacts list/show`, `pickPerson` over the store |
| `inbox` | `unreadIn`, `newIn`, `reviewIn` |
| `sync` | backfill (pages, ranges, estimate), `sync status`, export |

Paging arguments, `--offline` refusals and "not recorded yet" errors move with them, so a tool and a
command answer the same error for the same input.

**S3 · A session owns the lifecycle, and hands out the services.**

```ts
// src/services/session.ts
export interface Services { messages: MessagesService; chats: ChatsService; people: PeopleService;
  inbox: InboxService; sync: SyncService }
export type Override = (base: Services, deps: ServiceDeps) => Partial<Services>

export const withServices = <T>(context: MessengerContext, work: (services: Services) => Promise<T>): Promise<T>
```

`withServices` replaces `withMessenger` and `withStore` in commands: it builds `ServiceDeps` inside
`base.run` (so `--timeout`, run records and `track` stay as they are), runs `work`, then closes
whatever was opened. The MCP session builds `ServiceDeps` once and keeps them for its lifetime.

**S4 · Overrides by composition (NEED-408 A).** A CLI passes one `Override` in its
`ProgramDefinition`; the services a command gets are `{ ...base, ...override(base, deps) }`, merged
per service:

```ts
// max-cli, later: MAX's list checks the login delta before reading the store
const override: Override = (base) => ({
  messages: { ...base.messages, list: (chat, window) => maxList(base.messages, chat, window) },
})
```

No classes, no inheritance; the shared method is reachable as `base.messages.list`.

**S5 · Command factories stay, and gain `extend`.** `messagesCommand(messenger, { extend?: (messages:
Command) => void })` lets a CLI add or replace one subcommand without copying the factory. Commands
call `withServices` and render; nothing else.

**S6 · `stored` and `observed` stay decorators on the port.** Saving what a read answered is about the
port, not about a use case; keeping it there means a service never forgets to save. They move from
`src/cli/messenger/` to `src/services/` beside the deps that use them.

**S7 · A new entry point, `@leemour/cli-messaging/services`**, exporting the service types, the
factories, `ServiceDeps`, `Override`. The CLI entry keeps working.

## Work items

One PR each, based on `main`, each announced in `2026-09-29-parity-lanes.md` §4 first (the lanes edit
the same command files — a line saying "messages-command actions call `services.messages`; a new
subcommand adds a service method").

1. `src/services/` — `deps.ts`, `session.ts` (`withServices`, `Override` merge), `messages.ts` with
   `list`, `around`, `show`, `search`. `messages list|context|show|search` and the MCP
   `messages_list`/`messages_show`/`messages_context` tools call it. Move `stored`/`observed`.
   **Correction 2026-09-30 (built):** `show` is `around` with no neighbours, so it is not a method of its
   own; `after` reaches the service already parsed, so each caller keeps its own flag name in errors;
   the move of `stored`/`observed` waits for item 5 — the lanes edit `stored.ts`, and moving it gains
   nothing until the `./services` entry exists.
2. `messages` writes: `send`, `edit`, `delete`, `forward`, `pin`, `unpin`, `react` — the `guarded*`
   helpers become service methods; commands and tools switch.
3. `chats` and `people` services; their commands and tools switch.
4. `inbox` and `sync` services; `inbox`, `review`, `backfill`, `sync status`, `export` switch.
   **Correction 2026-09-30 (built):** #166 renamed the commands to `store fetch|status|export|jobs`, so
   the second service is `archive`, not `sync` (a `store` service would read as the message store
   itself). `inbox` has one `read` — unread, or with `since` what arrived after it — and `review`.
   `unreadIn`, `newIn` and `reviewIn` stay where they are: they are public exports with their own
   tests, and the service calls them. `store jobs` stays in its command, since it manages processes,
   not messages; it reads the held stretches through `archive.held`.
5. `Override` in `ProgramDefinition`; `extend` on command factories; the `./services` entry;
   `docs/dev/ARCHITECTURE.md` gets the layers.

## Tests

- **Services, directly**: each method against a scripted adapter and a store in a temp file —
  online saves what it read, offline reads it back, the guard refuses before the adapter is called.
  These replace nothing; they are the new unit.
- **Commands and MCP tools**: the existing suites pass without edits — that is the "no behaviour
  change" proof. tg-cli's suite runs against a local build (`bin/try-messaging`) before each release.
- **Override**: a test CLI replaces `messages.list`, calls the base inside, and both commands and
  tools see the replacement.
