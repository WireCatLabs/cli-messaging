# Drizzle for these stores — what it can and cannot do

2026-09-29. **Verified** = npm dist-tags or the published tarball read; **docs say** =
orm.drizzle.team or context7 `/drizzle-team/drizzle-orm-docs`; **inferred** = reasoning.

## Versions and drivers

- `drizzle-orm` stable **0.45.3** (2026-09-21); `beta` 1.0.0-beta.22; `rc` **1.0.0-rc.4**
  (2026-06-27). `drizzle-kit` stable 0.31.11, `rc` 1.0.0-rc.4 (verified: `npm view`).
- **SQLite:** `drizzle-orm/node-sqlite` exists **only from 1.0.0-beta.19** — not in 0.45.3
  (verified: package exports). `drizzle-orm/bun-sqlite` is in both lines. Both 1.0 SQLite drivers
  are **synchronous**; an async transaction callback is a type error (verified:
  `node-sqlite/session.d.ts:34`, `bun-sqlite/session.d.ts:36`). The connect pages install `@rc`
  ([node-sqlite](https://orm.drizzle.team/docs/connect-node-sqlite)); the request is open
  ([#2648](https://github.com/drizzle-team/drizzle-orm/issues/2648)).
- **Postgres:** `drizzle-orm/pglite`, `drizzle-orm/node-postgres` and pgvector helpers are in
  stable 0.45.3 (see [`2026-09-29-pglite-measured.md`](2026-09-29-pglite-measured.md)). Postgres
  drivers are async.
- Each SQLite driver imports its runtime module at the top of the file (verified), so a program
  that runs on Node and Bun must load them by dynamic `import()`.

## Migrations

- 1.0: one folder per migration (`migration.sql` + snapshot), tracked by **name** in
  `__drizzle_migrations`; 0.45 tracks by timestamp and silently skips a migration merged from an
  older branch (verified: `sqlite-core/dialect.js:660` vs `migrator.utils.js`). Old folders convert
  with `drizzle-kit up` ([upgrade-v1](https://orm.drizzle.team/docs/upgrade-v1)).
- In-code (bundled) migrations: documented for Expo and op-sqlite; the rc `bun-sqlite` migrator also
  takes an in-memory list, `node-sqlite` only reads a folder; `sqlite-core` exports `migrateSync`
  (verified, undocumented). Otherwise ship the folder in the npm package.
- An existing database: `drizzle-kit pull` introspects; `migrate(..., { init: true })` marks one
  migration applied on a database with no log (verified). A store versioned by `user_version` or
  `schema_migrations` needs a one-time bridge written by us (inferred). SQLite `pull` has open bugs on
  expression and partial indexes ([#6237](https://github.com/drizzle-team/drizzle-orm/issues/6237),
  [#6223](https://github.com/drizzle-team/drizzle-orm/issues/6223)).

## What stays SQL

- **SQLite FTS5 virtual tables and triggers are not modelled** (verified: no `fts5` in the rc
  tarball; request open, [#2046](https://github.com/drizzle-team/drizzle-orm/issues/2046)). They go
  in a `drizzle-kit generate --custom` migration ([custom migrations](https://orm.drizzle.team/docs/kit-custom-migrations)),
  and `MATCH`/`bm25()` queries use the `sql` tag.
- Postgres: `CREATE EXTENSION` is never emitted by drizzle-kit (verified) — a custom migration too.
  BM25 via `pg_textsearch` index/operator syntax would be `sql` as well (inferred).

## One schema for two databases

Not a feature (docs): `sqliteTable` and `pgTable` are separate builders, and a query typed against
one does not type-check against the other. "Database-agnostic" means two schema files and a store
interface we own (inferred).

## Size

drizzle-orm rc unpacks to 16 MB, 0.45.3 to 10.5 MB (verified: npm); drizzle-kit pulls esbuild and
jiti but is a dev dependency.

## Fair comparison with Kysely

Kysely: one query builder and one set of types for SQLite and Postgres; migrations are TypeScript
functions, in-code by design; custom SQLite drivers plug in through a small interface; 1.7 MB. But
async only, and migrations are written by hand. Drizzle: schema-first, migrations generated, sync
SQLite today; but two schema files for two dialects. The owner chose Drizzle (2026-09-29).
